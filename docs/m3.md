## Kết luận & số liệu chính xác (2026-07-29)

Vòng drone-in-a-box chạy **end-to-end trong MỘT world Gazebo duy nhất**, không
thao tác tay, không driver bơm lệnh:

```
drone bay tới box (GPS) → tự gửi REQUEST_LANDING → box mở nắp/kẹp THẬT (Gazebo)
→ box WAITING_FOR_LANDING(7) → drone hạ cánh thị giác lên marker trên thân box
→ chạm đất & disarm → box kẹp ngang/dọc + đóng nắp → drone gửi TURN_OFF_DRONE
→ box CHARGING(9).   Monitor thụ động: PASS 8/8.
```

**Số liệu đo được — đã kiểm, không phải cảm tính:**

### Bối cảnh

M2 đã nối được box-side (box_manager + adapter + Gazebo) và telemetry
bridge (MAVROS → dib_msgs). Nhưng phía drone, `offboard_precland_controller`
hiện **chưa nói chuyện với box**: nó có `st_goto_box()` bay tới box bằng
GPS offset và đã subscribe `BoxTelemetry` (đọc `box_lat_/box_lon_/box_yaw_`),
nhưng:
- **không gửi `REQUEST_LANDING`** → box không bao giờ mở nắp/kẹp cho nó.
- **không đọc `box_state`** → không biết box đã sẵn sàng chưa.
- `GOTO_BOX` chuyển thẳng sang `START` chỉ bằng bán kính GPS.

M3 lấp khoảng trống đó: drone chủ động yêu cầu box chuẩn bị, chờ box báo
sẵn sàng, rồi mới bắt đầu hạ cánh thị giác. Đây là mảnh ghép biến 2 nửa
đã chạy độc lập (M1/M2) thành 1 vòng khép kín.

### Hiện trạng code (đã có sẵn, tái dùng)

`offboard_precland_controller.hpp`:

- Đã có: `on_box_telemetry()`, `sub_box_telemetry_`, `box_lat_/box_lon_/box_yaw_`,

- Có `transition()` / `can_transition()` cho FSM; có sẵn client MAVROS
  (set_mode, arm, cmd, param) — **nhưng chưa có client `BoxCmd`**.

`box_state_manager.cpp` (hợp đồng phía box, đã verify):
- `REQUEST_LANDING` chỉ được nhận khi `agent_id % 10 == 2` **và** box đang
  EMPTY: `drone_id_ = agent_id / 10`. → Drone phải gửi
  `BoxCmd{command=REQUEST_LANDING(23), agent_id = drone_id*10 + 2}`.
- Box tự đi EMPTY→IDLE→PREPARING_FOR_LANDING→**WAITING_FOR_LANDING(7)**.
- `BoxTelemetry.box_state.state == 7` là tín hiệu "box sẵn sàng".
- Sau khi drone đáp, box tự WAITING_FOR_LANDING→SECURING_DRONE nhờ
  telemetry landed (bridge M2) — **drone KHÔNG cần gửi lệnh securing**.

### Thiết kế M3

#### FSM mới (thêm 2 state giữa GOTO_BOX và START)
```cpp
enum class PrecLandState {
  IDLE, FLIGHT_IN_PROGRESS, GOTO_BOX,
  PRELANDING_CHECK,   // MỚI
  WAIT_BOX_READY,     // MỚI
  START, HORIZONTAL_APPROACH, DESCEND_ABOVE_TARGET, FINAL_APPROACH,
  SEARCH, TARGET_LOST, FALLBACK, DONE
};
```
Luồng:
```
GOTO_BOX  --(tới bán kính box)-->  PRELANDING_CHECK
PRELANDING_CHECK  --(gimbal down, camera_info alive, tracker heartbeat OK)-->  WAIT_BOX_READY
PRELANDING_CHECK  --(fail/timeout)-->  FALLBACK
WAIT_BOX_READY    --(gọi REQUEST_LANDING 1 lần, poll box_state==7)-->  START
WAIT_BOX_READY    --(box_ready_timeout)-->  FALLBACK
START --> ... --> DONE   (giữ nguyên, không đụng)
```

#### Module mới: BoxLink
Tách riêng theo đúng pattern `refactoring_architecture.md` team đã đặt ra —
không nhét logic service vào file controller chính.
```
include/precision_landing/box_link.hpp
src/box_link.cpp

class BoxLink {
public:
  explicit BoxLink(rclcpp::Node* node, int box_id, int drone_id);
  void request_landing();          // BoxCmd{REQUEST_LANDING, agent_id=drone_id*10+2}, idempotent
  bool is_ready() const;           // box_state_.state == WAITING_FOR_LANDING(7)
  bool telemetry_fresh(double timeout) const;
  double box_lat() const; double box_lon() const; double box_yaw() const;
  // notify_landed() -> tùy chọn/tương lai: securing đã tự chạy qua telemetry M2
private:
  rclcpp::Client<dib_msgs::srv::BoxCmd>::SharedPtr cli_cmd_;      // /b<box_id>/cmd
  rclcpp::Subscription<dib_msgs::msg::BoxTelemetry>::SharedPtr sub_;  // /b<box_id>/telemetry
  dib_msgs::msg::BoxState box_state_;
  ...
};
```
> Có thể tái dùng luôn `sub_box_telemetry_` sẵn có thay vì tạo sub mới —
> quyết định lúc implement (gọn hơn: BoxLink sở hữu sub, controller bỏ sub cũ;
> hoặc controller đọc box_state rồi đẩy vào BoxLink). Ưu tiên BoxLink tự chủ.

Controller chỉ giữ `std::unique_ptr<BoxLink> box_link_;`.

#### Interface cụ thể 2 state mới
- **PRELANDING_CHECK** (`st_prelanding_check()`): xác nhận gimbal đã cụp
  (`gimbal_configured_`), `/gimbal_camera/camera_info` còn sống, target
  heartbeat `is_target_fresh()`. OK → WAIT_BOX_READY; timeout
  `prelanding_timeout` → FALLBACK. Vẫn stream setpoint giữ vị trí để PX4
  không rớt OFFBOARD.
- **WAIT_BOX_READY** (`st_wait_box_ready()`): gọi `box_link_->request_landing()`
  đúng 1 lần khi vào state; mỗi tick check `box_link_->is_ready()`. Ready →
  START; quá `box_ready_timeout_sec` → FALLBACK. Giữ setpoint như trên.

#### Tham số mới
```
box_id (int, default 1)              # để dựng /b<box_id>/cmd
drone_id (int, default 1)            # agent_id = drone_id*10 + 2
prelanding_timeout_sec (10.0)
box_ready_timeout_sec (30.0)
```

### Các thay đổi file

### Bối cảnh

M3 chứng minh **luồng phần mềm** khép kín (bắt tay drone↔box, FSM hai bên).
Nhưng ở 7b, box và drone chạy trong **hai tiến trình Gazebo, hai world tách
biệt**: drone hạ xuống `dib_box_landing_pad` — một model **tĩnh, chỉ có visual,
không có joint nào** — trong khi nắp/kẹp thật cử động ở world khác của
`box_simulation`.

Nói cách khác, hiện có hai nửa rời nhau:
- `dib_box_landing_pad`: **nhìn thấy được** (có marker) nhưng **bất động**
- `box.xacro`: **cử động được** (nắp, kẹp, ros2_control) nhưng **vô hình với
  camera** — grep ra chỉ toàn màu trơn `Gazebo/Orange|Blue|Grey|Black`, không
  có marker nào

M3.5 gộp hai nửa đó lại: một box **vừa cử động vừa nhìn thấy được**, đứng trong
chính world mà PX4 đang mô phỏng.

**Đây KHÔNG phải điều kiện để M3 đúng** — 7b đã đủ chứng minh logic. M3.5 phục
vụ **sản phẩm đóng gói**: video drone bay tới → box mở nắp → drone hạ vào trong
→ kẹp đóng lại, quay trong một world duy nhất.

### Vì sao trước đây tưởng là không hợp nhất được

`ros_gz_sim create` gọi service qua gz transport → spawn vào **bất kỳ gz server
nào đang chạy**, không gắn với world rỗng đó. Bỏ action `gazebo` đi là box vào

Plugin **system** (Harmonic, build từ source) nạp đúng, nhưng khi nó nạp tiếp
plugin **hardware** qua pluginlib thì vớ phải bản **apt Fortress**. Truyền

**Cùng loại bug với M2 nhưng ở tầng khác**, và đây là điểm dễ nhầm nhất:
- plugin **system** tìm qua `GZ_SIM_SYSTEM_PLUGIN_PATH`
- plugin **hardware** tìm qua **pluginlib** → `AMENT_PREFIX_PATH` + `LD_LIBRARY_PATH`

→ `export GZ_SIM_SYSTEM_PLUGIN_PATH=...` **KHÔNG đủ**. Env hook của ws cũng chỉ
set `LD_LIBRARY_PATH`, không set `GZ_SIM_SYSTEM_PLUGIN_PATH`.

Vì sao M2 không dính: ở 6a, Gazebo do `box_full_stack.launch.py` khởi động từ
terminal **đã source ws**. Ở M3.5, gz server do **PX4** khởi động ở T1 — nếu T1
không source ws thì server chỉ thấy `/opt/ros/humble`.

**Sửa (chọn 1):**
```bash

# B. Triệt để (khuyến nghị) — gỡ hẳn bản apt Fortress

```

> - **(a) Tính:** ép marker rơi đúng `(4.0,-3.5)` → phải giải chuỗi biến đổi
>   model→world qua phép xoay `-R 1.57`. Đây đúng là phép tính đã khiến nhận

> lon = 8.546163739800146  + (E / (6378137.0 * cos(lat0))) * 180/pi

#### Việc KHÔNG làm trong M3.5
- Không bridge `navsat` của box (vẫn dùng fixture `box_gps_publisher.py`).

  > **Nếu sau này bridge navsat thật: phải TÍNH LẠI offset, KHÔNG khôi phục
  > giá trị cũ.** (Đính chính nhận định trước đó cho rằng chúng "khớp".)
  >
  > Cơ chế (`box_state_manager.cpp:17-23,187-196`):
  > ```
  > LLtoUTM(lat, lon, yG, xG, zone)   // yG = Northing, xG = Easting
  > xG += x_off*cos(yaw) - y_off*sin(yaw)
  > yG += x_off*sin(yaw) + y_off*cos(yaw)
  > UTMtoLL(yG, xG, zone, box_info.lat, box_info.lon)
  > ```
  > → `box_info = antenna + R(yaw_box)·(x_off Đông, y_off Bắc)`, tức offset là
  > vector **từ antenna tới điểm quy chiếu của box**.
  > Xác nhận bằng 7b lần 1: fixture publish tâm pad (4.00,−3.50), box_info ra
  > (3.84,−1.60), chênh (−0.16 E, +1.90 N) = đúng (x_off, y_off) với yaw_box=0.
  >
  > `gps_joint` trong `box.xacro` = `xyz="-0.21299 1.94386 -1.33887"`, là vector
  > **base_link → antenna trong hệ model đang xoay**. Áp spawn `-R 1.57`
  > (`model (x,y,z) → world (x, -z, y)`):
  >
  > | | yaml | URDF suy ra (antenna→base_link) | |
  > |---|---|---|---|
  > | Đông | −0.15 | **+0.213** | ngược dấu |
  > | Bắc | +1.9 | **−1.339** | ngược dấu, lệch độ lớn |
  > | Lên | −1.5 | −1.944 | cùng dấu, lệch độ lớn |
  >
  > Hai bộ số cùng mô tả một cột antenna vật lý (1.9 vs 1.944; 0.15 vs 0.213 —
  > quá sát để là ngẫu nhiên), nhưng yaml `(−0.15, +1.9)` trùng với **model x,y
  > thô**, tức trông như được chép thẳng từ URDF mà bỏ qua phép xoay và bỏ qua
  > chiều vector. Mà `y = 1.944` trong hệ model chính là trục **thẳng đứng** sau
  > khi xoay, không phải trục ngang.
  >
  > ⚠️ **P0.1 sẽ đổi tư thế spawn → ánh xạ model→world đổi theo → offset phải
  > tính lại lần nữa.** Vì vậy chỉ tính sau khi P0.1 chốt xong.
  >
  > `z_anten_gps_offset` là **code chết** cho luồng hạ cánh: `zG` được cộng
  > nhưng `UTMtoLL` chỉ nhận Northing/Easting, và `box_info` không set altitude.
