## Kết luận & số liệu (2026-08-05)

```
box ROS_DOMAIN_ID=42  <--DDS-Router 2.2.0-->  drone ROS_DOMAIN_ID=0
(chỉ 3 giao diện hợp đồng + 1 fixture SITL đi qua cầu, mọi thứ khác cục bộ)

drone bay tới box → tự gửi REQUEST_LANDING (topic, qua cầu)
→ box mở nắp/kẹp thật, WAITING_FOR_LANDING(7) (qua cầu, telemetry box→drone)
→ drone hạ cánh thị giác, chạm đất & disarm (telemetry drone→box, qua cầu)
→ box kẹp + đóng nắp + cắt điện → drone gửi TURN_OFF_DRONE (qua cầu)
→ d1/telemetry im (qua fixture /dock/drone_power, qua cầu) → box CHARGING(9)
```

| Đại lượng | Giá trị | Ghi chú |
|---|---|---|
| Sai số bám hạ cánh (`aim_error`), lần PASS cuối | **2.2 cm** | `TOUCHDOWN` log, split-domain |
| Sai số yaw, lần PASS cuối | **0.01°** | cùng dòng `TOUCHDOWN` |
| Thời gian `POWER_OFF → CHARGING` sau khi cắt điện | **~4.6 s** | khớp ngưỡng thiết kế 5 s staleness của `securing_state_manager.cpp` |

# Phụ lục A — Bề mặt cầu (giao diện hợp đồng, đọc từ code)

**3 giao diện hợp đồng** (có cả trên phần cứng thật):

| Interface | Kiểu | Hướng | QoS |
|---|---|---|---|
| `b2/telemetry` | topic `dib_msgs/msg/BoxTelemetry` | box(42) → drone(0) | default |
| `d1/telemetry` | topic `dib_msgs/msg/DroneTelemetry` | drone(0) → box(42) | **BEST_EFFORT/VOLATILE** |
| `b2/drone_cmd` | topic `dib_msgs/msg/BoxCmd` (`REQUEST_LANDING`/`TURN_OFF_DRONE`) | drone(0) → box(42) | default |

**+1 fixture chỉ cho SITL** (bỏ trên phần cứng thật):

| Interface | Kiểu | Hướng | QoS |
|---|---|---|---|
| `/dock/drone_power` | topic `std_msgs/msg/Bool` | box(42) → drone(0) | **RELIABLE/TRANSIENT_LOCAL** |

`/dock/drone_power` giả lập việc box cắt điện dock. Trên phần cứng thật, cắt
điện làm máy tính drone tắt hẳn nên `d1/telemetry` im miễn phí; trong SITL
MAVROS vẫn chạy nên phải báo bằng topic. Box chỉ rời `POWER_OFF → DONE →
CHARGING` khi `d1/telemetry` im quá 5 s (`securing_state_manager.cpp`) —
**thiếu fixture này thì box kẹt vĩnh viễn ở `SECURING_DRONE`** (xem sự cố
thật ở Phụ lục E.2).

Mọi thứ khác cục bộ một bên, **không bắc cầu**: bên drone có MAVROS + PX4 +
tracker + gz bridges; bên box có `/gps`, `/lid|clamp|dock/*`, ros2_control
của box. `use_sim_time`/`/clock` cũng không bắc cầu — mỗi domain tự chủ đồng
hồ, đúng như phần cứng thật.

# Phụ lục B — Hai nút thắt kỹ thuật đã gỡ (2026-08-05)

## B.1 — `whitelist-interfaces`, không phải lỗi version

Kết luận cũ (2026-07-30) "DDS-Router 2.2 cần `ROS_LOCALHOST_ONLY=0`" là
**triệu chứng**, không phải nguyên nhân. Bắt gói multicast bằng socket UDP
thường (join `239.255.0.1:7400/7650`, không cần root) cho thấy: dưới
`ROS_LOCALHOST_ONLY=1`, SPDP **vẫn chảy hai chiều bình thường** giữa router
và node ROS. Nghẽn thật nằm ở tầng sau: node ROS chỉ whitelist `127.0.0.1`
và **âm thầm loại** mọi locator không nằm trên interface đó; DDS-Router
(Fast DDS thuần) bind mọi interface và quảng bá cả IP LAN thật → locator
SEDP/unicast của nó bị loại → không cặp Reader/Writer nào khớp.

**Sửa:** thêm `whitelist-interfaces: ["127.0.0.1"]` vào **từng participant**
trong config (đây là tag **per-participant**, parse ở
`ddspipe_yaml/src/cpp/YamlReader_participants.cpp` — KHÔNG phải tag
top-level, dễ đặt sai chỗ). Sau khi sửa: talker(0)→listener(1) qua cầu sạch
dưới `ROS_LOCALHOST_ONLY=1`, không cần nới lỏng cấu hình mạng của SITL.

**Bẫy phụ đi kèm — type tuỳ biến cần khai `type` tường minh trong
allowlist.** Cấu hình "không allowlist, bridge mọi thứ" bắc cầu được
`std_msgs/String` (demo talker/listener) nhưng mang **0 message** cho
`dib_msgs/BoxCmd` trong cùng điều kiện. Phải khai cả tên lẫn type
DDS-mangled:
```yaml
allowlist:
  - name: "rt/b2/drone_cmd"
    type: "dib_msgs::msg::dds_::BoxCmd_"   # <ros_pkg>::msg::dds_::<MsgName>_
```

## B.2 — Service `/b2/cmd`: bug thật, không sửa được → bỏ khỏi đường bắc cầu

Test lại với `whitelist-interfaces` đã đúng **và** `ROS_LOCALHOST_ONLY=1`,
dùng service ROS 2 chuẩn (`demo_nodes_cpp add_two_ints_server` domain 0 +
`ros2 service call` domain 1) để loại trừ yếu tố `dib_msgs`: server log
`Incoming request a: 3 b: 4` (**request qua được**), client treo,
**không bao giờ có reply**. Đây là lỗi RPC-bridge thật của DDS-Router
2.2.0, độc lập hoàn toàn với nút B.1 — đo với cả message tuỳ biến lẫn
generic, đều mất reply như nhau.

**Quyết định:** thay vì ghép thêm `domain_bridge` chỉ để cõng một service,
chuyển lệnh drone→box từ service `b2/cmd` sang **topic** `b2/drone_cmd`
(`dib_msgs/msg/BoxCmd`, thêm field `command`/`reserve`/`agent_id` additive
vào message có sẵn). An toàn vì reply cũ vốn đã vô nghĩa:
`box_state_manager::box_cmd_callback()` set `response->success = true`
**ngay dòng đầu** rồi mới ném việc sang thread rời — comment trong
`box_link.hpp` từ M3 đã ghi rõ "telemetry mới là hợp đồng thật", không phải
reply của service. Service `b2/cmd` **vẫn giữ nguyên** cho vai trò
operator/server (`agent_id % 10 == 0`, người vận hành gọi trực tiếp) — chỉ
là vai trò đó không còn cần đi qua ranh giới domain.

Kết quả: **DDS-Router giờ là cầu duy nhất cần thiết**, không phải ghép hai
công cụ.

# Phụ lục C — Vì sao bản DDS-Router mới nhất (3.x) không dùng được

| Thành phần | Fast DDS |
|---|---|
| ROS 2 Humble (`rmw_fastrtps`) | **2.6.11** (`libfastrtps.so.2.6`) |
| DDS-Router 3.5.1 (build lần 1, 2026-07-30) | **3.6.1** (`libfastdds.so.3.6`) |
| DDS-Router 3.5.1 (build lại lần 2, 2026-08-05, kiểm tra chéo) | **3.6.1** — kết quả giống hệt |
| DDS-Router 2.2.0 (bản dùng thật) | **2.14.0** (`libfastrtps.so.2.14`) |

Kiểm `.repos` của từng tag DDS-Router: `v3.0.0→3.0.1`, `v3.4.0→3.4.1`,
`v3.5.1→3.6.1` — **toàn bộ dòng 3.x đều pin Fast DDS 3.x**, nên hạ xuống
"3.4" cũng vô ích. Chứng minh dứt điểm: build `hello_world` Fast DDS **3.6**
thuần, router 3.6 bắc cầu — subscriber 3.6 (domain 1) **nhận** publisher 3.6
(domain 0) bình thường; nhưng cùng router đó bắc cầu talker/listener
**ROS-2.6** kinh điển thì **không gì qua**, thử cả hai giá trị
`ROS_LOCALHOST_ONLY`. Khác biệt duy nhất là 2.6 so với 3.6 ⇒ một participant
Fast DDS 3.6 không discovery được endpoint Fast DDS 2.6.

Đo lại lần hai (2026-08-05, bản build mới, không phải dùng lại kết quả cũ)
cho kết quả **giống hệt** — không phải trùng hợp một lần. Router link Fast
DDS nào là quyết định **lúc build từ `.repos`**, không có tham số cấu hình
nào đổi được ở runtime. DDS-Router 2.2.0 pin Fast DDS 2.14.0, vẫn thuộc
dòng 2.x, nói chuyện được với 2.6 — đó là lý do chọn bản "cũ" thay vì bản
mới nhất.

# Phụ lục D — Chứng minh cầu THẬT SỰ mang dữ liệu (không phải domain rò rỉ)

DDS-Router 2.2.0 **không log từng message** — đã kiểm cả `-d` lẫn
`--log-verbosity info --log-filter ".*"`, vẫn chỉ in `DDS Router running.`
rồi im. Bằng chứng lấy từ ba nguồn khác, cả ba đều mạnh hơn một dòng log.

**1. Socket mạng — cứng nhất.** ROS 2 ánh xạ `ROS_DOMAIN_ID` sang cổng UDP
theo công thức cố định `7400 + 250 × domain`: domain 0 → 7400, domain 42 →
17900. Đo bằng `ss -uapn`:

| Tiến trình | Domain | Cổng UDP đang giữ |
|---|---|---|
| `box_side.py` | 42 | `17900`, multicast `239.255.0.1:17900`, 17912, 17913 — **không có 7400** |
| `drone_side.py` | 0 | `7400`, multicast `239.255.0.1:7400`, 7410, 7411 — **không có 17900** |
| `ddsrouter` | — | **`7400` VÀ `17900`**, cả unicast lẫn multicast |

Hai node ROS nghe hai cổng vật lý khác nhau nên **không thể nghe thấy
nhau**; router là tiến trình **duy nhất** đứng chân ở cả hai domain. Mọi
message qua được đều buộc phải đi qua nó — bằng chứng loại trừ, không phải
suy luận. Tự kiểm lại:
```bash
ps -eo pid,cmd | grep -F ddsrouter | grep -v grep
ss -uapn | grep -F "pid=<PID>" | awk '{print $4}' | sort -t: -k2 -n
```

**2. Nhân quả.** Tầng-1: tắt router giữa chừng → drone vẫn publish `#6`,
`#7` nhưng box **dừng nhận** ngay sau `#5`. M4.1 (chưa bật cầu): loop kẹt ở
`WAIT_BOX_READY`/`EMPTY` ngay từ đầu.

**3. Nội dung log ứng dụng.** Mỗi dòng dưới đây là một message đã **vượt
ranh giới domain**, vì bên phát và bên nhận nằm ở hai domain khác nhau:

| Dòng log | Ở đâu | Bên phát |
|---|---|---|
| `Drone command received: 23` | box, domain 42 | `BoxLink`, domain 0 |
| `Drone telemetry connected=1` | box, domain 42 | `mavros_to_dib_telemetry`, domain 0 |
| `BoxLink: box_state 7 -> 8` | drone, domain 0 | `box_state_manager`, domain 42 |
| `Dock power OFF: stopping publishing d1/telemetry` | drone, domain 0 | `box_hardware_adapter`, domain 42 |

# Phụ lục F — Cầu dự phòng (`dib_domain_bridge` / `domain_bridge`)

Giữ lại có chủ đích, không phải bản nháp bỏ quên: cài từ apt trong vài

sau này cần lại (DDS-Router 2.2.0 thì không, xem Phụ lục B.2).

`ros2_ws/src/dib_domain_bridge/src/dib_split_bridge.cpp` đã sửa khớp code
mới: bắc cầu `b2/drone_cmd` như một **topic** (drone→box) thay vì service
`b2/cmd` như bản cũ, cộng đúng 3 giao diện hợp đồng + fixture
`/dock/drone_power`. Tầng-1 chạy lại cùng bộ script (`tier1/`) → PASS: 6/6
`REQUEST_LANDING` tới box, `b2/telemetry` tới drone. "Dự phòng" là bản đã đo
thật, không phải lý thuyết.

```bash
ros2 run dib_domain_bridge dib_split_bridge 42 0   # arg1=box domain, arg2=drone domain
```

# Phụ lục H — Ngoài phạm vi M4

- Hai domain trên **hai máy vật lý thật** (LAN thật) — M4 làm trên một host
  (hai domain cùng máy) trước; tách máy thật thuộc M5 hardening. Chỉ chuẩn
  bị sẵn ghi chú cách chỉnh `whitelist-interfaces` cho LAN thật.
- Đa drone / đa box (`agent_id = drone_id*10 + 2` đã hỗ trợ ở tầng code
  nhưng chưa test).
- Bảo mật DDS (SROS2) → M5.
